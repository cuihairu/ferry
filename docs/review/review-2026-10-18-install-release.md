## 一、总体目标

本轮不新增业务功能，优先修复现有实现中影响安装、注册、安全和生产部署的问题。

目标是形成一个可验证的最小交付闭环：

**首次部署 → 安全初始化 → 管理员登录 → 节点注册 → Agent 连接 → 配置下发 → 状态与流量上报 → 升级回滚 → 数据备份恢复。**

### 执行约束

1. 开始前检查当前分支、HEAD、工作区状态及 `todo.md`，不得覆盖其他 Agent 的未提交修改。
2. 先检查当前代码和测试，确认问题仍然存在后再修改，不得仅根据历史分析直接改代码。
3. 不得为了让测试通过而移除 API 鉴权、降低安全校验或修改既有业务契约。
4. 不得把单元测试通过、代码覆盖率达标等同于生产环境验收通过。
5. 每个任务必须包含问题证据、实现方案、测试证据和剩余风险。
6. 完成后更新 `todo.md`，记录实际修改文件和测试结果；没有实际提交就不得编造 commit hash。
7. 不自动重开已有的外部阻塞项或明确裁决为不做的需求。

## P0：必须优先处理

### FERRY-001：修复 Agent 一键注册的认证闭环

**现状问题**

- `deploy/agent-install.sh` 中的 `--register` 会直接调用 `POST /api/nodes`。
- `/api/nodes` 属于受 `apiAuth()` 保护的管理 API。
- 安装请求没有携带认证凭据，当前注册逻辑与服务端鉴权要求不一致。

**实现要求**

- 复核 Agent 安装、节点创建、节点令牌签发和 API 鉴权的完整调用链。
- 为首次节点注册设计安全的授权方式。
- 优先考虑短时、一次性、仅允许注册节点的 enrollment token。
- 如果采用其他方案，必须明确凭据权限、有效期、撤销方式和泄露影响。
- 不得开放匿名节点创建，不得取消 `/api` 的全局鉴权。
- 注册成功后，只将节点运行所需的节点令牌写入 Agent 配置，不得把管理员凭据或完整管理 API Token 持久化到节点。
- 下载、参数验证和二进制校验应在服务端创建节点之前完成，避免安装失败留下孤立节点。
- 对注册响应进行可靠的 JSON 解析，不得依赖容易受字段格式影响的简单文本截取。

**验收标准**

- [ ] 无注册凭据时，服务端拒绝请求且数据库不新增节点。
- [ ] 合法注册凭据可以创建节点，并安全取得节点令牌。
- [ ] 过期、已使用或无效的注册凭据均被拒绝。
- [ ] 重复提交不会创建重复节点。
- [ ] 二进制下载或校验失败时，不会留下未完成注册记录。
- [ ] 安装日志不输出完整令牌或其他敏感凭据。
- [ ] 新增服务端认证测试和安装流程测试。
- [ ] 更新安装文档和 `todo.md`。

### FERRY-002：打通正式 Release 与 `latest` 安装流程

**现状问题**

- 安装脚本默认 `VERSION=latest`。
- 下载路径会将版本拼成 `vlatest`。
- 当前仓库没有正式 GitHub Release，夜间构建产物不能替代长期稳定的正式发行渠道。

**实现要求**

- 为稳定版本建立正式发布流程，由版本标签触发构建。
- 产出与安装脚本约定一致的 Agent 二进制包，以及可选的 QUIC sidecar 包。
- 支持 Linux amd64 和 arm64，明确每种架构实际发布的产物。
- 为每个压缩包生成 SHA-256 校验文件。
- 将构建产物和校验文件发布到对应的 GitHub Release。
- `--version latest` 必须解析实际最新稳定版本，再构建下载地址。
- 指定版本时必须下载对应版本，不得静默回退到其他版本。
- 没有可用稳定版本、缺失资产或校验失败时，应立即失败并给出明确错误。
- 默认正式发行包不得在缺少校验文件时静默跳过校验。

**验收标准**

- [ ] 从版本标签到 Release 资产的命名规则一致。
- [ ] `latest` 能解析为真实稳定版本，而不是字面上的 `vlatest`。
- [ ] 指定版本和默认版本均有自动化测试。
- [ ] 缺失资产、下载失败、校验失败均能正确失败。
- [ ] Release 流程包含构建、测试、打包、校验文件和资产上传。
- [ ] 至少在干净的 Linux 环境验证下载、安装和启动。
- [ ] README 与安装脚本的版本说明一致。

### FERRY-003：建立生产环境密钥安全门禁

**现状问题**

当前部分配置在密钥为空时会回退到开发用常量。主密钥缺失还会影响云凭证的加密存储。

**实现要求**

- 区分首次初始化、开发环境和生产环境。
- 对管理员签名密钥、API Token 签名密钥及敏感数据加密主密钥建立明确的初始化规则。
- 新安装时，可以生成随机密钥并持久保存到 `.env`，不得每次启动都重新生成。
- 已有数据库如果缺少加密主密钥，应停止危险操作并给出恢复或迁移指引，不得直接替换密钥导致已有数据不可解密。
- 生产环境不得静默使用已知的开发默认密钥。
- 对密钥长度、格式和配置冲突进行校验。
- 不得在日志、健康检查响应或前端中暴露密钥。
- 保证已有 `.env` 不被启动脚本覆盖。

**验收标准**

- [ ] 新安装可安全初始化所需密钥。
- [ ] 重启后密钥保持稳定。
- [ ] 生产环境缺少必要密钥时明确拒绝启动或进入受控的初始化流程。
- [ ] 已有数据库和配置不会因重复启动而被覆盖。
- [ ] 验证敏感凭证的加密、解密和密钥缺失行为。
- [ ] 增加配置校验测试及首次部署测试。
- [ ] 更新 `.env.example`、部署文档和安全设计文档。

### FERRY-004：增加端到端部署与节点通信测试

**目标**

当前单元测试覆盖率不能替代真实部署链路验证。建立一套可在 CI 中重复执行的集成测试。

**测试范围**

- [ ] 从干净环境执行 Docker Compose 配置检查和部署。
- [ ] 验证服务健康状态、数据库初始化和持久化。
- [ ] 验证管理员首次登录和管理 API 鉴权。
- [ ] 使用测试 Agent 完成节点注册及 WebSocket 握手。
- [ ] 验证配置下发、Agent 应答和服务端状态更新。
- [ ] 验证 Agent 断线、重连和重复消息处理。
- [ ] 验证节点令牌轮换、兼容窗口和吊销。
- [ ] 验证数据库备份、恢复以及恢复后的登录和节点数据。
- [ ] 验证 dash 和用户 panel 的静态资源、API 路由及页面刷新。
- [ ] 将稳定且不依赖真实第三方服务的测试纳入 CI。

**验收标准**

- 集成测试必须实际启动相关服务，而不是只 mock 所有组件。
- 测试环境使用隔离的临时数据，不能操作真实部署的数据。
- 测试失败时能够输出关键服务日志和失败步骤。
- 不得因为集成测试困难而删除已有单元测试或降低 CI 门禁。

### FERRY-005：让 Agent 安装与升级具备失败恢复能力

**现状风险**

安装脚本会下载、替换二进制、写配置并重启 systemd 服务。需要验证中途失败时，节点不会进入不可恢复状态。

**实现要求**

- 安装前验证操作系统、架构、必填参数、二进制和校验文件。
- 所有必要资产下载并校验成功后，才执行安装和节点注册。
- 使用临时目录准备新版本，并以原子替换方式更新二进制。
- 替换前保留当前可用版本，失败时能够恢复。
- 重启后检查服务实际状态和 Agent 连接结果。
- 启动失败时提供明确诊断，并按安全规则回滚。
- 已存在的配置、节点标识和必要的密钥材料必须得到保护。
- 对注册失败、磁盘空间不足、下载中断、校验失败、服务启动失败等情况分别测试。

**验收标准**

- [ ] 安装失败不会破坏原有可运行版本。
- [ ] 升级失败后可以恢复原版本。
- [ ] 已有配置不会被意外覆盖。
- [ ] 安装和升级操作具有清晰的日志及退出码。
- [ ] 不支持的系统或架构会在修改系统前失败。
- [ ] 增加可重复的脚本测试，必要时使用模拟 systemd 的测试环境。

### FERRY-001：修复 Agent 一键注册的认证闭环

**现状问题**

- `deploy/agent-install.sh` 中的 `--register` 会直接调用 `POST /api/nodes`。
- `/api/nodes` 属于受 `apiAuth()` 保护的管理 API。
- 安装请求没有携带认证凭据，当前注册逻辑与服务端鉴权要求不一致。

**实现要求**

- 复核 Agent 安装、节点创建、节点令牌签发和 API 鉴权的完整调用链。
- 为首次节点注册设计安全的授权方式。
- 优先考虑短时、一次性、仅允许注册节点的 enrollment token。
- 如果采用其他方案，必须明确凭据权限、有效期、撤销方式和泄露影响。
- 不得开放匿名节点创建，不得取消 `/api` 的全局鉴权。
- 注册成功后，只将节点运行所需的节点令牌写入 Agent 配置，不得把管理员凭据或完整管理 API Token 持久化到节点。
- 下载、参数验证和二进制校验应在服务端创建节点之前完成，避免安装失败留下孤立节点。
- 对注册响应进行可靠的 JSON 解析，不得依赖容易受字段格式影响的简单文本截取。

**验收标准**

- [ ] 无注册凭据时，服务端拒绝请求且数据库不新增节点。
- [ ] 合法注册凭据可以创建节点，并安全取得节点令牌。
- [ ] 过期、已使用或无效的注册凭据均被拒绝。
- [ ] 重复提交不会创建重复节点。
- [ ] 二进制下载或校验失败时，不会留下未完成注册记录。
- [ ] 安装日志不输出完整令牌或其他敏感凭据。
- [ ] 新增服务端认证测试和安装流程测试。
- [ ] 更新安装文档和 `todo.md`。

### FERRY-002：打通正式 Release 与 `latest` 安装流程

**现状问题**

- 安装脚本默认 `VERSION=latest`。
- 下载路径会将版本拼成 `vlatest`。
- 当前仓库没有正式 GitHub Release，夜间构建产物不能替代长期稳定的正式发行渠道。

**实现要求**

- 为稳定版本建立正式发布流程，由版本标签触发构建。
- 产出与安装脚本约定一致的 Agent 二进制包，以及可选的 QUIC sidecar 包。
- 支持 Linux amd64 和 arm64，明确每种架构实际发布的产物。
- 为每个压缩包生成 SHA-256 校验文件。
- 将构建产物和校验文件发布到对应的 GitHub Release。
- `--version latest` 必须解析实际最新稳定版本，再构建下载地址。
- 指定版本时必须下载对应版本，不得静默回退到其他版本。
- 没有可用稳定版本、缺失资产或校验失败时，应立即失败并给出明确错误。
- 默认正式发行包不得在缺少校验文件时静默跳过校验。

**验收标准**

- [ ] 从版本标签到 Release 资产的命名规则一致。
- [ ] `latest` 能解析为真实稳定版本，而不是字面上的 `vlatest`。
- [ ] 指定版本和默认版本均有自动化测试。
- [ ] 缺失资产、下载失败、校验失败均能正确失败。
- [ ] Release 流程包含构建、测试、打包、校验文件和资产上传。
- [ ] 至少在干净的 Linux 环境验证下载、安装和启动。
- [ ] README 与安装脚本的版本说明一致。

# Ferry：面向 Code Agent 的 TODO 建议

## 一、总体目标

本轮不新增业务功能，优先修复现有实现中影响安装、注册、安全和生产部署的问题。

目标是形成一个可验证的最小交付闭环：

**首次部署 → 安全初始化 → 管理员登录 → 节点注册 → Agent 连接 → 配置下发 → 状态与流量上报 → 升级回滚 → 数据备份恢复。**

### 执行约束

1. 开始前检查当前分支、HEAD、工作区状态及 `todo.md`，不得覆盖其他 Agent 的未提交修改。
2. 先检查当前代码和测试，确认问题仍然存在后再修改，不得仅根据历史分析直接改代码。
3. 不得为了让测试通过而移除 API 鉴权、降低安全校验或修改既有业务契约。
4. 不得把单元测试通过、代码覆盖率达标等同于生产环境验收通过。
5. 每个任务必须包含问题证据、实现方案、测试证据和剩余风险。
6. 完成后更新 `todo.md`，记录实际修改文件和测试结果；没有实际提交就不得编造 commit hash。
7. 不自动重开已有的外部阻塞项或明确裁决为不做的需求。

## P0：必须优先处理

### FERRY-001：修复 Agent 一键注册的认证闭环

**现状问题**

- `deploy/agent-install.sh` 中的 `--register` 会直接调用 `POST /api/nodes`。
- `/api/nodes` 属于受 `apiAuth()` 保护的管理 API。
- 安装请求没有携带认证凭据，当前注册逻辑与服务端鉴权要求不一致。

**实现要求**

- 复核 Agent 安装、节点创建、节点令牌签发和 API 鉴权的完整调用链。
- 为首次节点注册设计安全的授权方式。
- 优先考虑短时、一次性、仅允许注册节点的 enrollment token。
- 如果采用其他方案，必须明确凭据权限、有效期、撤销方式和泄露影响。
- 不得开放匿名节点创建，不得取消 `/api` 的全局鉴权。
- 注册成功后，只将节点运行所需的节点令牌写入 Agent 配置，不得把管理员凭据或完整管理 API Token 持久化到节点。
- 下载、参数验证和二进制校验应在服务端创建节点之前完成，避免安装失败留下孤立节点。
- 对注册响应进行可靠的 JSON 解析，不得依赖容易受字段格式影响的简单文本截取。

**验收标准**

- [ ] 无注册凭据时，服务端拒绝请求且数据库不新增节点。
- [ ] 合法注册凭据可以创建节点，并安全取得节点令牌。
- [ ] 过期、已使用或无效的注册凭据均被拒绝。
- [ ] 重复提交不会创建重复节点。
- [ ] 二进制下载或校验失败时，不会留下未完成注册记录。
- [ ] 安装日志不输出完整令牌或其他敏感凭据。
- [ ] 新增服务端认证测试和安装流程测试。
- [ ] 更新安装文档和 `todo.md`。

### FERRY-002：打通正式 Release 与 `latest` 安装流程

**现状问题**

- 安装脚本默认 `VERSION=latest`。
- 下载路径会将版本拼成 `vlatest`。
- 当前仓库没有正式 GitHub Release，夜间构建产物不能替代长期稳定的正式发行渠道。

**实现要求**

- 为稳定版本建立正式发布流程，由版本标签触发构建。
- 产出与安装脚本约定一致的 Agent 二进制包，以及可选的 QUIC sidecar 包。
- 支持 Linux amd64 和 arm64，明确每种架构实际发布的产物。
- 为每个压缩包生成 SHA-256 校验文件。
- 将构建产物和校验文件发布到对应的 GitHub Release。
- `--version latest` 必须解析实际最新稳定版本，再构建下载地址。
- 指定版本时必须下载对应版本，不得静默回退到其他版本。
- 没有可用稳定版本、缺失资产或校验失败时，应立即失败并给出明确错误。
- 默认正式发行包不得在缺少校验文件时静默跳过校验。

**验收标准**

- [ ] 从版本标签到 Release 资产的命名规则一致。
- [ ] `latest` 能解析为真实稳定版本，而不是字面上的 `vlatest`。
- [ ] 指定版本和默认版本均有自动化测试。
- [ ] 缺失资产、下载失败、校验失败均能正确失败。
- [ ] Release 流程包含构建、测试、打包、校验文件和资产上传。
- [ ] 至少在干净的 Linux 环境验证下载、安装和启动。
- [ ] README 与安装脚本的版本说明一致。

### FERRY-003：建立生产环境密钥安全门禁

**现状问题**

当前部分配置在密钥为空时会回退到开发用常量。主密钥缺失还会影响云凭证的加密存储。

**实现要求**

- 区分首次初始化、开发环境和生产环境。
- 对管理员签名密钥、API Token 签名密钥及敏感数据加密主密钥建立明确的初始化规则。
- 新安装时，可以生成随机密钥并持久保存到 `.env`，不得每次启动都重新生成。
- 已有数据库如果缺少加密主密钥，应停止危险操作并给出恢复或迁移指引，不得直接替换密钥导致已有数据不可解密。
- 生产环境不得静默使用已知的开发默认密钥。
- 对密钥长度、格式和配置冲突进行校验。
- 不得在日志、健康检查响应或前端中暴露密钥。
- 保证已有 `.env` 不被启动脚本覆盖。

**验收标准**

- [ ] 新安装可安全初始化所需密钥。
- [ ] 重启后密钥保持稳定。
- [ ] 生产环境缺少必要密钥时明确拒绝启动或进入受控的初始化流程。
- [ ] 已有数据库和配置不会因重复启动而被覆盖。
- [ ] 验证敏感凭证的加密、解密和密钥缺失行为。
- [ ] 增加配置校验测试及首次部署测试。
- [ ] 更新 `.env.example`、部署文档和安全设计文档。

### FERRY-004：增加端到端部署与节点通信测试

**目标**

当前单元测试覆盖率不能替代真实部署链路验证。建立一套可在 CI 中重复执行的集成测试。

**测试范围**

- [ ] 从干净环境执行 Docker Compose 配置检查和部署。
- [ ] 验证服务健康状态、数据库初始化和持久化。
- [ ] 验证管理员首次登录和管理 API 鉴权。
- [ ] 使用测试 Agent 完成节点注册及 WebSocket 握手。
- [ ] 验证配置下发、Agent 应答和服务端状态更新。
- [ ] 验证 Agent 断线、重连和重复消息处理。
- [ ] 验证节点令牌轮换、兼容窗口和吊销。
- [ ] 验证数据库备份、恢复以及恢复后的登录和节点数据。
- [ ] 验证 dash 和用户 panel 的静态资源、API 路由及页面刷新。
- [ ] 将稳定且不依赖真实第三方服务的测试纳入 CI。

**验收标准**

- 集成测试必须实际启动相关服务，而不是只 mock 所有组件。
- 测试环境使用隔离的临时数据，不能操作真实部署的数据。
- 测试失败时能够输出关键服务日志和失败步骤。
- 不得因为集成测试困难而删除已有单元测试或降低 CI 门禁。

### FERRY-005：让 Agent 安装与升级具备失败恢复能力

**现状风险**

安装脚本会下载、替换二进制、写配置并重启 systemd 服务。需要验证中途失败时，节点不会进入不可恢复状态。

**实现要求**

- 安装前验证操作系统、架构、必填参数、二进制和校验文件。
- 所有必要资产下载并校验成功后，才执行安装和节点注册。
- 使用临时目录准备新版本，并以原子替换方式更新二进制。
- 替换前保留当前可用版本，失败时能够恢复。
- 重启后检查服务实际状态和 Agent 连接结果。
- 启动失败时提供明确诊断，并按安全规则回滚。
- 已存在的配置、节点标识和必要的密钥材料必须得到保护。
- 对注册失败、磁盘空间不足、下载中断、校验失败、服务启动失败等情况分别测试。

**验收标准**

- [ ] 安装失败不会破坏原有可运行版本。
- [ ] 升级失败后可以恢复原版本。
- [ ] 已有配置不会被意外覆盖。
- [ ] 安装和升级操作具有清晰的日志及退出码。
- [ ] 不支持的系统或架构会在修改系统前失败。
- [ ] 增加可重复的脚本测试，必要时使用模拟 systemd 的测试环境。
