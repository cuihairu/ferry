## 0. 调研对象与取材方式

- Remnawave：入口仓 `remnawave/panel`（GitHub）——现为文档站与发布入口（docusaurus 源码在仓内 `docs/`，无 Go/TS 代码）；实现在 `remnawave/backend`（面板后端）、`remnawave/frontend`（管理端 React）、`remnawave/node`（节点）、`remnawave/xtls-sdk`（Xray-core 的 TS SDK）。来源：`docs/overview/components.md`。
- 取材：浅克隆 `remnawave/backend`（2026-10-08 快照）逐文件阅读；文档引用 `panel` 仓 `docs/` 下的 mdx 源文件。
- **更正一处常见说法**：Remnawave 后端不是 Go——`package.json` 依赖 `@nestjs/core 11.2.1`、`@prisma/client 6.19.3`，源码 `src/` 全量 TypeScript（NestJS + Prisma + PostgreSQL）；节点（`remnawave/node`）同为 TypeScript，容器内嵌 Xray-core（经 `@remnawave/xtls-sdk` 包 Xray API，见 `components.md` 对 SDK 的描述）。「Go 面板」是误传。

## 1. Remnawave 逐机制调研（文件级来源）

### 1.1 节点与编队模型（三层：节点 / 主机 / 编队）

- **节点（Nodes）**不自带入站配置：挂 `activeConfigProfileUuid` 引用配置档案。`prisma/schema.prisma` 的 `Nodes` 模型（L164-220）：`isConnected/isConnecting/isDisabled` 连接状态机、`consumptionMultiplier/nodeConsumptionMultiplier` 消费倍率（默认 1e9=1.0x）、`countryCode/tags/ips`、`providerUuid` 关联供应商（`InfraProviders`/`InfraBilling*` 机器账单与预算）。
- **配置档案（ConfigProfiles）**存 Xray 配置模板，`ConfigProfileInbounds` 是档案内入站，`ConfigProfileInboundsToNodes` 把入站指派给节点——选配哪个入站在 Web UI 里做（官方对比表 "Selecting active inbounds on nodes" 行，对照 Marzban 走节点环境变量）。
- **主机（Hosts）**是面向用户的连接信息层（分享出去的地址/伪装）：`Hosts` 模型（schema L267-315）含 `address/port/path/sni/host/alpn/fingerprint/securityLayer`、`xhttpExtraParams/muxParams/sockoptParams`、`excludeFromSubscriptionTypes`（按订阅格式排除）、`internalSquadsMode`（EXCLUDE/ALLOW_ONLY）；经 `HostsToNodes` 绑定到节点。
- **编队（Squads）**=批量分发单位：`InternalSquads`（内部编队——`InternalSquadHostLinks` 绑主机、`InternalSquadInbounds` 绑入站、`InternalSquadMembers` 收用户，用户挂 `externalSquadUuid` 单选）与 `ExternalSquads`（外部编队——跨面板共享订阅清单，`ExternalSquadsTemplates`）。
- 节点流量也有预算面：`Nodes.trafficLimitBytes/trafficUsedBytes/trafficResetDay/notifyPercent`（schema L188-191）——节点级限额、重置日与告警百分比。

### 1.2 订阅面（sub 形态）

- 六种响应格式：`RESPONSE_RULES_RESPONSE_TYPES` = `MIHOMO / CLASH / STASH / SINGBOX / XRAY_BASE64 / XRAY_JSON`（`src/modules/subscription-template/constants/config-types.ts`）；生成器一一对应（`src/modules/subscription-template/generators/{clash,mihomo,singbox,xray-json,xray}.generator.service.ts`）。
- 模板可多套（`SubscriptionTemplate` + `render-templates.service.ts`），另有响应规则（`subscription-response-rules`，按 UA/设备路由到不同格式）与全局订阅设置（`subscription-settings`）。
- 订阅页独立成模块：`SubscriptionPageConfig`（自建订阅落地页，官方对比表 "Multiple subscription pages" 行称可装多页）。
- 订阅标识用短 ID：`Users.shortUuid`（schema L48）。

### 1.3 流量记账与配额

- 用户实时用量是**单行表**：`UserTraffic`（schema L86-102）`usedTrafficBytes/lifetimeUsedTrafficBytes/onlineAt/lastConnectedNodeUuid/firstConnectedAt`——在线态与最近接入节点一并落行；不是逐条流水（对照 ferry `traffic_logs` 逐条记账）。
- 历史聚合两张表：`NodesUserUsageHistory`（用户×节点）与 `NodesUsageHistory`（节点级，schema L234/L251）。
- 用户配额：`trafficLimitBytes` + `trafficLimitStrategy`（`NO_RESET/DAY/WEEK/MONTH/MONTH_ROLLING`，schema L54）——**MONTH_ROLLING 滚动窗口**（按上次重置时间滚动一个月）是 ferry `reset_cycle`（none/day/week/month）没有的档；`lastTrafficResetAt` 记上次重置。
- 用户状态四态：`ACTIVE/DISABLED/LIMITED/EXPIRED`（schema L50-51）——超限（LIMITED）与到期（EXPIRED）分开表达；官方对比表确认无 Marzban 式 "On Hold" 暂缓起算态。
- 凭证在用户行上预生成：`trojanPassword/vlessUuid/ssPassword`（schema L57-59），主机层组装分享链接。

### 1.4 用户触达与告警

- 双通道：Telegram + Webhook，**逐事件逐通道开关**——配置文件 `configs/notifications/notifications-config.yml` 挂载进容器（`docs/features/fine-tuned-notifications.md`，2.3.1+），形如 `events: user.created: {telegram: true, webhook: false}`。
- 事件面覆盖：用户增删改、`user.bandwidth_usage_threshold_reached`（用量阈值如 80%/90%）、节点上下线、节点流量阈值、`user_hwid_devices.added`（新设备绑定）、`errors.bandwidth_usage_threshold_reached_max_notifications`（达通知上限自限流防刷，同文件 L108-109/L174/L217-218）。
- 阈值防重复推送靠字段记忆：`Users.lastTriggeredThreshold` 记已触发的档位，配额变更时清零（`src/modules/users/users.service.ts` L167）。
- Webhook 带签名：`X-Remnawave-Signature`（`WEBHOOK_SECRET_HEADER` 签名）+ `X-Remnawave-Timestamp`（`docs/features/receiving-webooks.md`；URL 支持逗号分隔多个）。
- 内置 TG bot 只做通知与 TG OAuth 登录（管理员侧，`docs/features/telegram-oauth.md`），不做用户自助查询命令。
- 其他：HWID 设备数限制（`Users.hwidDeviceLimit` + `HwidUserDevices`）、种子拦截上报（`TorrentBlockerReports` 表）、rescue-cli 管理员自救（`docs/features/rescue-cli.md`）。

### 1.5 部署形态

- 最小部署即三容器：`remnawave/backend:3` + `postgres:18.4` + `valkey/valkey:9-alpine`（`docker-compose-prod.yml`）——PostgreSQL 与 Valkey 是硬依赖，无 SQLite 档。
- advanced 编排拆三个 backend 服务：`remnawave-rest-api / remnawave-scheduler / remnawave-processor`（`docker-compose-advanced-prod.yml`）——API/定时任务/队列消费分进程。
- 官方系统要求：面板 2GB RAM / 2 核 / 20GB 盘（`docs/overview/comparison-of-functions.md` 官方表 System requirements 行；同表标注 Marzban 1GB 为社区口径）。
- 官方对比表（同文件，自述为「前 Marzban 用户经验、不唯一可靠来源」）其余有参照价值的行：配置存 DB（对照 Marzban 文件）、配置校验带 XRAY 全量校验、节点断联仍工作、无 VMESS host 面（需 core 级配置补）、无多管理员、HWID 设备限制独有。

## 3. 对 ferry（单机小内存定位）的取舍参考

只作观察，不引新工：

1. **形态判定**：Remnawave 的三层模型（配置档案/主机/编队）+ 三容器硬依赖 + 官方 2GB RAM 建议，是面向规模化多机运营的形态；ferry 的节点/池态/入口两层模型在单机内闭环覆盖同类编排诉求，SQLite 缺省档与「小内存 VPS」定位自洽——**维持现状，不因对齐而动**。
2. **可留观的机制**（ferry 已有等价物或收益有限）：
   - `MONTH_ROLLING` 滚动重置档：ferry `reset_cycle` 无此档，小站自然月账单（TOUCH-4）已够用，挂观察；
   - `lastTriggeredThreshold` 阈值档位记忆：ferry 预警面用同日去重+触达记录（TOUCH-5），机制等价；
   - Webhook 出站签名头：ferry 事件面是 outbox+Herald 回执（方向相反：ferry 是生产方），形态不同不需对齐；
   - 节点级流量预算+告警百分比（`Nodes.notifyPercent`）：ferry 节点侧有探测与池态机，流量预算未做，若日后多机放量再议（挂观察，不开工）。
3. **反面清单**（不抄）：三容器起步与 PostgreSQL/Valkey 硬依赖与单机小内存定位相悖；订阅页/响应规则/编队三层对当前规模是过度设计；TG bot 只做通知不做自助查询（ferry TOUCH-6 的只读对接面已覆盖自助查询且不依赖面板域名存活）。
4. **取材纠正存档**：社区常把 Remnawave 当「Go 面板」，实为 TS/NestJS——后续引用其作为「Go 同类实现」的场合应更正。
