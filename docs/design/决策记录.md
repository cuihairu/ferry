# 决策记录（代决关闭项）

只登记**已代决关闭**的扩充项：判断「现在不做」并给出被否选项与重开触发条件。
凭据/商户资质、上游发布、真机环境、复现观察类外部等待项不在此列——仍挂
`todo.md` 的 `[BLOCKED]` 行，等外部材料到位再开。

代决授权边界（2026-10-14）：设计/需求类可自行代决；**版本号/发版、License 变更、
付费采购、素材授权**四类留用户，不进本表。

## 1. mTLS CA 编排：不建编排，维持手签脚本

- **方案**：面板侧不做 CA 编排。自签 CA 与按节点签发维持 `deploy/mtls-ca.sh init|issue`
  两步手工；agent 侧三件套经 TLSConfig 声明（`agent/internal/config/config.go:15-18`，
  全部为空时仅节点令牌走系统根证书校验），安装脚本 `--ca/--cert/--key` 传入
  （`deploy/README.md`「mTLS 证书生成」节）。
- **被否选项**：面板内自动签发 + 到期轮换编排——需新增 CA 私钥管理面、到期提醒、
  批量重签与吊销同步，是纯前置成本。
- **理由**：mTLS 消费方为零（默认关闭），编排对象不存在；节点规模未达「手工签发
  不可维持」的量级（每节点两条命令）。
- **重开触发**：mTLS 消费方 ≥1 且节点数使手工签发不可维持，或用户点名。

## 2. 调度历史权重自动调参：不做，维持人工配置

- **方案**：不做基于历史负载的权重自动漂移；权重维持人工配置——权重口径见
  《调度核心设计》§1「采集维度 → 决策权重映射表」（每个采集字段对应一个权重），
  当前由面板侧人工给定。
- **被否选项**：历史延迟/失败驱动的自动权重更新（含回滚策略与「人工覆盖优先序」
  设计）——工程量集中在算法校准，不是功能价值。
- **理由**：单站规模人工调参已满足；自动调参需要历史分布与真实故障样本，当前无
  数据可校准，误调比不调更糟。
- **重开触发**：多机放量且人工调参出现瓶颈，或用户点名。

## 3. 节点级流量预算与告警百分比：不做，维持用户级配额

- **方案**：不做 per-node 预算与百分比告警；维持用户级月流量配额
  （`server/internal/storage/models.go:94` MonthlyTrafficQuotaBytes）与节点流量
  记账现状。
- **被否选项**：节点预算阈值 + 百分比告警——新增告警通道负载与阈值调参面。
- **理由**：单站规模下节点总量与流量在 dash 节点列表已可见；无对应的告警疲劳或
  成本诉求，先行实现只会产出噪音告警。
- **重开触发**：多机部署出现且需要节点级预算约束，或用户点名。

## 4. 多区域控制面：不做，维持单点控制面（F-9901 评估）

- **评估背景**：控制面 = 单二进制 ferry（server）+ sqlite；agent 全量经 WS 连到
  唯一 server。多区域控制面的可能动机逐项评估如下。
- **动机 (a) 跨区 agent 可达性/RTT**：agent→server 只承载低频控制流（周期心跳、
  配置下发回执、流量采样），对 RTT 不敏感；数据面流量走 entry→landing（可经
  relay）直连，不经 server。agent 断连有 spool 离线缓冲（probe 角色）与自重连，
  控制流短暂不可达不丢数据面。**不构成多区域需求。**
- **动机 (b) 控制面可用性**：已按「控制面短时不可用不停数据面」设计（F-1932
  dataplane-test 断言宕机窗口内核存活；《面板可用性设计》故障语义分层）；恢复
  路径有同数据目录重启零操作回池（reconnect-test）与状态恢复（F-2053）。HA 升级
  已由 F-1946/F-1947 评估收口：单点 + 手动提升 standby，不做自动故障转移——比
  多区域部署便宜一个量级且先覆盖同一风险。**已被更便宜的方案覆盖。**
- **动机 (c) 数据驻留/合规**：ferry 定位部署者自持的单站部署工具（《合规定位
  声明》），无跨区驻留诉求。**不成立。**
- **被否选项**：多区域控制面（每区域 server 副本 + 全局配置同步/分片 + server
  间仲裁）——同时引入配置一致性、调度权威分裂（与决策「Server 是全局调度权威」
  直接冲突）、跨区 DB 复制三个新问题，而上述三个动机无一成立。
- **重开触发**：出现「某区域节点到唯一 server 持续不可达」的真实拓扑，或部署者
  要求控制面异地容灾，或用户点名。

## 5. 高级多跳 Path：不做，维持三段式 Path（F-9904 评估）

- **评估背景**：现状 Path = Entry + 可选 Relay + Landing 三段固定形状
  （`server/internal/handler/paths.go:21-104`，RelayNodeID 为空即直连形状）；
  PathGroup 表达候选集合，按位次 + 探测健康挑路径（`pathhealth.ResolveGroupPath`）。
  todo §22 决策 #8 已钉「先完成 Entry→Landing 两段式，不提前引入任意多跳图调度」，
  此条补评估论证。
- **多跳诉求拆解**：(a) 串联更多跳绕路/分流——数据面收益存疑：每多一跳多一跳
  RTT 与带宽税，且 relay 现为单流 TCP io.Copy（F-0812 行留证），本就是吞吐瓶颈，
  加跳数放大瓶颈；(b) 故障绕行——已有更便宜的解：PathGroup 候选按健康切换 +
  区域/运营商聚合摘挂（《入口与负载均衡设计》C.4.3）+ relay 腿可空可回落直连
  形状，多跳是同一问题的更贵解；(c) 链路隐匿——不在《合规定位声明》主张范围内。
- **成本面**：任意多跳图把调度从「路径选择」变「图路由」：config 下发形状、
  探测维度（逐跳 probe）、记账归属、quota 链路全部重做，并与已落地的候选组语义
  （F-0611 族）冲突。
- **被否选项**：任意 N 跳图调度 / 多跳链式 relay。
- **重开触发**：出现「直连与单 relay 均不可达而两跳可达」的真实线路样本，或
  用户点名。
