# 告警通道设计（对接 Herald）

目标：ferry **不自建投递通道**——事件（管理告警 + 用户触达）统一投递 Herald（自家开源事件投递基建），通道分发（TG/微信/邮件等）由 Herald 管。ferry 侧只做事件生产与集成接口。

## 1. 定位与分工

```
ferry（事件源）                    Herald（投递基建）              通道
┌──────────────┐  ①POST /events   ┌──────────────┐  路由规则   ┌──────┐
│ 区域故障/被封/  │ ───────────────→ │ 事件接入       │ ─────────→│ TG   │
│ 费用超阈/证书到 │  ②outbox 落库重试 │ 去重/路由/重试  │           │ 微信  │
│ 期/进程崩溃/…  │                  │ 模板渲染       │           │ 邮件  │
│ 用户触达(账单等)│                  │ 投递回执       │           │ Webhook│
└──────────────┘                  └──────────────┘           └──────┘
```

| 职责 | ferry | Herald |
| --- | --- | --- |
| 事件产生（含区域/运营商合并后的单条告警） | ✅ | —— |
| 事件语义（kind/severity/target/dedup_key） | ✅ | —— |
| 通道接入、模板、路由、去重、限频、重试 | —— | ✅ |
| 投递回执与失败上报 | 收结果落 `event_deliveries` | ✅ |

## 2. 事件类型清单

### 2.1 管理告警（dash/管理员通道）

| kind | 来源 | 严重度 | 接入 |
| --- | --- | --- | --- |
| `region_fault` | 区域聚合判定（合并告警，一区域一条） | critical | ✅ HERALD-3 |
| `isp_fault` | 运营商聚合判定 | critical | ✅ HERALD-3（同点位） |
| `node_blocked` | 被封检测（单节点） | critical | ✅ HERALD-3 |
| `node_down` | 单点摘挂/心跳丢失 | warning | ✅ HERALD-3（池自动摘除；复位/手动不发） |
| `cost_exceeded` | 费用超阈值（切流提示） | warning | ✅ HERALD-3（告警激活即发，活跃去重沿用） |
| `cert_expiring` | 证书临近到期 | warning | ✅ HERALD-3 |
| `proc_crashed` | 进程崩溃拉起失败 | warning/critical | ✅ HERALD-3（服务端告警激活点，active 唯一性去重） |
| `recovery_failed` | 恢复流水线超时全失败（升级人工） | critical | ✅ HERALD-3（与 node_blocked 同点位） |
| `backup_failed` | 面板备份失败 | warning | ✅ P1 备份批（周期备份失败/方言不支持，本地按日自查重） |
| `login_alert` | 管理员登录异常（连续失败/异网段成功） | warning | ✅ P1 安全批（登录审计接生产点，15min 窗口失败≥5 次/异网段成功，本地按日自查重） |
| `price_alert` | 价格关注命中（降价/目标价到位） | warning | ✅ E-32 参考库批（价格关注扫描接生产点，降价=较上快照下降、到位=目标价跨越沿只发一次，本地按日自查重） |

接入点位（2026-10-08 HERALD-3，事件经 outbox 投递，Emit 失败只记日志不阻断主流程）：区域/运营商整体故障迁移（monitor）、判封开线与恢复失败升级（recovery，BR-5 webhook 通道并行期保留）、证书进续期窗口（cert，同域名同日一条）、池自动摘挂（pool，仅 suspend）、成本告警激活（cost）、进程崩溃告警激活（handler 告警落库点）。

### 2.2 用户触达（按用户通道，见《用户触达设计》）

`bill` 月账单 / `domains` 域名清单 / `expire` 到期 / `quota` 流量预警 / `order` 订单结果 / `notice` 公告。

已有生产点接入（2026-10-08 HERALD-4，target=`user:<id>`，severity=info）：到期提醒与流量预警（notifyscan 扫描，站内信已落才发、去重随通知日闸门）、发放到账（applyGrant 事务内同原子，dedup 带 order_no）、公告扇出（notice 事件与站内信同批落，禁用用户不收；公告为管理侧主动动作不设 dedup_key）。`bill`/`domains` 随触达批调度器落地时接同一接口。站内信照发不裁撤——本通道供站外投递（邮件/TG 等，由 Herald 分发）。

## 3. 集成接口

```json
// POST {FERRY_HERALD_URL}/events    （Header: Authorization: Bearer {Herald Token}）
{
  "kind": "region_fault",
  "severity": "critical",
  "title": "华东区域入口整体不可达",
  "body": "窗口 60s 内 3/3 节点 sick，已整区域切走",
  "target": "admin",            // admin / user:<id>
  "dedup_key": "region:华东:region_fault",  // 去重键，窗口内同键合并
  "meta": { "region": "华东", "count": 3 },
  "occurred_at": "2026-10-05T20:31:00+08:00"
}
```

- **去重**：区域/运营商合并告警在 ferry 侧先聚合（一个维度一条），`dedup_key` 兜底防重复风暴；
- **回执**：Herald 异步回投 `POST {ferry}/api/internal/event-results`，ferry 落 `event_deliveries`（sent/failed，detail 列宽 512），重试由 Herald 管；
- 配置：`FERRY_HERALD_URL`、`FERRY_HERALD_TOKEN`；未配置时事件只落本地 outbox（dash 可见），不阻塞主流程。

**落地口径（2026-10-08 HERALD-2）**：投递腿 `herald.HTTPSender(url, token)`——POST `{url}/events`，token 非空带 `Authorization: Bearer`，10s 超时，2xx 即成功（否则进 outbox 退避重试）；载荷在 §3 格式上加 `id` 扩展字段（ferry outbox 主键），Herald 回执带回该 id 做关联。回执端点 `POST /api/internal/event-results`（`{event_id, channel, status: sent|failed, detail}`）逐条落 `event_deliveries`，事件本体状态不动（ferry→Herald 腿 2xx 已置 sent，通道分发与重试由 Herald 管）；鉴权与 reconcile 同口径（无鉴权 `/api` 组，部署侧以网络边界隔离）。`main.go` 按 `FERRY_HERALD_URL` 装配 sender，未配置=只落库不尝试。

**落地口径（2026-10-08 HERALD-5）**：回执端点原生解析 herald §13.5 事件回调（`{event_id: "cb-…", app, kind, at, delivery: {…}}`，herald 侧 `core/callback/emitter.go` 的签名与载荷为第一手口径）——双形状判别：外层 `event_id` 是 JSON 字符串=§13.5（取 `delivery.event_id` 字符串解析为 ferry outbox id、`delivery.channel`→channel、`delivery.status` success/failed→sent/failed、`delivery.error`→detail；`unsubscribe` 等无 `delivery` 的回调 200 ack 忽略，防 herald at-least-once 重试刷），是 JSON 数字=HERALD-2 旧形状原样继续收（线上 shim 通道不断流，shim 可平迁退役）。验签 `X-Herald-Signature: sha256=<hex HMAC-SHA256>` 覆盖原始请求体，密钥 `FERRY_HERALD_CALLBACK_SECRET`（对应 herald 侧 `PUT /api/v1/apps/ferry/callback` 设置的 32 字节 secret，常量时间比对）；**空=不验签**（沿用 HERALD-2 网络边界隔离口径，既有通道不断；配置后强制验签，缺前缀或不匹配统一 401——shim 等无签名投递方需同步升级或直连）。触达联动（TOUCH-5）对两种形状同走 `touchResult`。

## 4. 可靠性：本地 outbox（已落地 2026-10-08 HERALD-1）

```
事件产生 → outbox 落库（pending）
        → 投递 Herald → 成功置 sent / 失败按指数退避重投
        → 超过阈值仍未成功 → dash 标红提示（通道故障不静默丢事件）
```

- 面板离线/Herald 不可达时事件不丢，恢复后补投（对齐《面板可用性设计》的降级语义）。

**落地口径（`server/internal/herald`）**：生产侧 `herald.Emit` 落 pending 即返回（不碰网络）；投递循环 `herald.Loop`（`FERRY_EVENT_FLUSH_SEC` 默认 30s）取到期 pending 逐条投递——每次尝试落 `event_deliveries`（channel=herald）留痕；失败退避 1m→2m→4m→…封顶 1h，连败 6 轮置 `failed` 死信（dash 标红，事件不删，修复后可人工重投 POST /api/events/:id/retry）。**未配置通道（FERRY_HERALD_URL 为空）时事件只落库 dash 可见，不尝试不烧次数**。dash 通知页带 outbox 卡：三状态计数（failed>0 红标）+ 状态过滤 + 死信重投按钮。管理端只读+重投：GET /api/events（status/kind/limit 过滤带计数）。

## 5. 数据模型

```sql
-- 事件 outbox 与投递结果
CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    kind TEXT NOT NULL,
    severity TEXT NOT NULL,
    title TEXT NOT NULL,
    body TEXT NOT NULL DEFAULT '',
    target TEXT NOT NULL,                 -- admin / user:<id>
    dedup_key TEXT,
    meta TEXT,                            -- JSON
    status TEXT NOT NULL DEFAULT 'pending', -- pending/sent/failed
    attempts INTEGER NOT NULL DEFAULT 0,  -- 投递尝试次数（退避/死信依据）
    next_attempt_at DATETIME,             -- 下次重试时间
    occurred_at DATETIME NOT NULL,
    created_at DATETIME NOT NULL
);
CREATE INDEX idx_events_pending ON events(status, created_at);

CREATE TABLE event_deliveries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    event_id INTEGER NOT NULL REFERENCES events(id) ON DELETE CASCADE,
    channel TEXT NOT NULL,                -- tg/email/wechat/webhook
    status TEXT NOT NULL,                 -- sent/failed
    detail TEXT,
    at DATETIME NOT NULL
);
```
